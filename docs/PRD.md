## 2. 판정 계약 (출력 스키마) — 4값 고정

| verdict | 의미 | evidence_link | search 수행 |
|---|---|---|---|
| `REFUTED` | falsifier 기준을 **전부** 충족하는 반례 문서가 실재 | **필수** | O |
| `NOT_REFUTED` | N개 쿼리를 돌렸으나 기준 충족 반례 미발견. **"사실이다"라는 뜻이 아님** | 항상 NULL | O |
| `PUBLIC_SUBSTANTIATION_NOT_FOUND` | 실증이 필요한 유형인데 공개 근거 자체가 확인되지 않음 | NULL | O |
| `PUFFERY` | 주관적 과장 표현. 검증 대상이 아님 | N/A | **X (0회)** |

**절대 하지 않는 것:**
- 신뢰도 점수(%) 출력 — "87% 확신" 같은 숫자는 무엇을 측정하는지 정의할 수 없습니다. 경쟁 제품이 이걸로 무너지는 지점이라 우리는 의도적으로 안 만듭니다.
- "참/거짓" 판정 — 우리는 최초임을 인증하지 않습니다. 원리적으로 불가능합니다. **반례의 존재 여부만 보고합니다.**
- "허위/거짓/위법/사기" 같은 법적 결론 어휘 — 출력 게이트에서 차단합니다.

`NOT_REFUTED`는 반드시 **"우리가 실행한 이 N개 쿼리에서 발견하지 못했다"**로 축자 표기하고, 실행한 쿼리 전문을 화면에 렌더링합니다. 반증 불가능한 명제를 반증 가능한 절차 기록으로 바꾸는 것이 이 판정의 목적입니다.

## 4. 불가침 규칙 (Non-negotiables) — 시간이 없어도 지킬 것

### N1. REFUTED 게이트는 결정론적 코드로 강제한다
LLM이 "이건 반례입니다"라고 선언한다고 REFUTED가 되면 안 됩니다. `falsifier_spec.required_match_fields`에 정의된 필드가 **전부 true**일 때만 애플리케이션 코드가 REFUTED를 조립합니다.

```python
verdict = "REFUTED" if all(
    candidate.applicability_check[f]
    for f, required in falsifier_spec.required_match_fields.items() if required
) else "NOT_REFUTED"
```

**왜 중요한가**: "국내 1위"는 다른 회사도 1위라고 광고했다는 사실만으로 깨지지 않습니다. 동일 기간·지표·시장 정의의 비교 자료여야 합니다. 이 게이트가 없으면 아무 문서나 갖다 붙이고 REFUTED를 확정하는 오판정이 실제로 나갑니다. **사람이 검수하는 단계가 설계상 존재하지 않으므로, 이것이 유일한 정확성 방어선입니다.**

### N2. 사람이 판정을 게이트하지 않는다
사용자 피드백(👍/👎)은 **판정이 이미 출력된 뒤에** 비동기로 받습니다. 어떤 경우에도 사람의 승인을 기다렸다가 응답을 내보내는 코드 경로를 만들지 마세요. §3-1 위반입니다.

### N3. 검색이 먼저, 판정은 그 다음
LLM이 먼저 답을 생성하고 검색이 구색만 맞추는 구조 금지. 검색 결과(근거)가 존재하고, 그 안에서만 판정이 나오는 구조여야 합니다.

### N4. PUFFERY는 검색 이전에 걸러진다
`PUFFERY` 판정 시 검색 tool_call이 **0건**이어야 합니다. 이것이 데모에서 "에이전트가 검색을 거부하고 이유를 설명하는" 장면을 만듭니다.

### N5. claim_type은 고정 vocabulary다
업종 카테고리(`industry_category`)는 동적으로 생성됩니다. 하지만 `claim_type`(SUPERLATIVE_FIRST, RANKING 등 — falsifier_spec과 연결되어 REFUTED 기준을 결정)은 **절대 동적 생성하지 않습니다.** 판정 기준 자체를 LLM이 즉흥 생성하면 N1이 무의미해집니다.

### N6. 근거를 지어내지 않는다
반례를 못 찾으면 `NOT_REFUTED`입니다. URL이나 날짜를 추론해서 채우지 마세요. `evidence_link`는 검색 결과에 실제로 존재한 URL만 들어갑니다.

## 5. LINER / OpenAI 역할 분리 (트랙 요구사항 핵심)

**LINER = 검색 실행자 (2개 모델 고용)**
- LINER Web Search — 일반 사실관계 반례 탐색
- LINER Scholar Search — 학술/임상 근거 반례 탐색

**OpenAI = 그 외 전부**
- 이미지 이해, 클레임 원자화, PUFFERY 판별, 라우팅, 반증 가설 수립, 검색 쿼리 생성, 증거 적용가능성 판단, 임베딩, 최종 판정 조립, 출력 가드레일

이 경계를 코드에서 명확히 유지하세요. **OpenAI의 내장 web_search 툴은 사용하지 않습니다** — 검색은 전부 LINER를 통합니다. (이유는 `DECISIONS.md` D-04 참조)

상세 모델 배정은 `MODELS_AND_APIS.md`.

## 6. 차별화 논리 (Q&A에서 반드시 필요)

### "그냥 ChatGPT한테 물어보면 되지 않나요?"
답은 나옵니다. 차이는 세 가지입니다.
1. **감사 가능성** — "없는 것 같습니다"는 검색을 안 해서인지 진짜 없어서인지 구분 불가. 우리는 실행 쿼리 전문과 실패 과정을 남깁니다.
2. **결정론적 반례 기준** — 반례로 인정되려면 scope/metric/timeframe/target이 전부 일치해야 하고, 이 판단은 LLM 자유서술이 아니라 코드가 강제합니다.
3. **누적 재사용** — 검증된 클레임은 canonical로 쌓이고, 유사 질문이 오면 재검색 없이 답하거나 시간 간극만큼만 좁혀서 재검색합니다.

### "이게 해자가 있나요?"
**과장하지 마세요.** 정직한 답:
> "지금 시점에 강한 해자가 있다고 주장하지 않겠습니다. 갖고 있는 건 오판정을 막는 결정론적 구조와, 축적된 증거 위에 간극만큼만 얹어 재검증하는 캐시입니다. 델타 서치는 오늘 새로 진입하는 경쟁사가 할 수 없습니다 — 얹을 과거 증거가 없으니까요. 강한 해자는 이후 만들어질 자산이라고 정직하게 말씀드립니다."

## 7. 즉석 태스크 대응 (Real-time Adaptability 25%)

| 심사위원이 던지는 것 | 시스템 반응 |
|---|---|
| 아무 광고 캡처 | 정상 동작, 문구별 4값 판정 |
| puffery ("우리 김밥이 제일 맛있다") | `PUFFERY`, tool_call 0건, 분류 근거만 표시 |
| 하이퍼로컬 ("이 해커톤은 국내 최초 YAI×OpenAI 공동 해커톤") | `NOT_REFUTED` + 실행 쿼리 목록 + "참임을 증명한 것이 아님" 축자 문구 |
| 학술 근거 주장 ("임상적으로 입증된") | LINER **Scholar** 경로로 라우팅 (스트림에서 색이 다르게 보임) |
| **사전 정의에 없는 완전 신규 업종** (장례서비스, 드론 방제 등) | 기존 카테고리와 유사도 비교 → 미달 → **그 자리에서 신규 카테고리 생성** 후 정상 판정 |
| 이미 처리한 적 있는 클레임 재입력 | 캐시 히트, 재검색 없이 즉시 응답 (지연시간 차이가 화면에 보임) |

마지막 두 줄이 이 제품의 결정적 시연 지점입니다.

## 9. 팀 분담 (중요)

**변경됨 (2026-08-01, Streamlit 단일 배포 결정 이후)**: 원래 계획은 "우리=백엔드+DB+이벤트 스트림 API / 다른 팀원=프론트엔드+DB 시각화"로 역할을 분리하는 것이었습니다. **이제 Streamlit 배포가 이 프로젝트의 최종 산출물이며, 프론트엔드·DB 시각화 역할까지 이 저장소가 전부 흡수합니다.** 별도 팀원 프론트엔드는 없습니다.

이에 따라:
- 백엔드 오케스트레이션(S0~S6) + DB + **Streamlit UI(입력 화면, 판정 결과, 세컨드 화면용 raw trace 뷰, `/v1/stats` 상당의 대시보드)**를 전부 이 저장소에서 만듭니다.
- 기존에 "다른 팀원이 붙을 API 계약을 먼저 고정"해야 했던 이유(§구 버전)는 더 이상 적용되지 않습니다. 다만 백엔드 로직과 UI 렌더링 사이의 **내부 계약**(파이프라인 함수 시그니처, `trace_event` 테이블 스키마)은 여전히 먼저 고정하는 게 좋습니다 — 테스트 가능성과 "왜 이 순서인가"를 코드로 증명하는 Pipeline Architecture 배점(25%)에는 여전히 중요합니다.
- 상세 내용은 `DECISIONS.md` D-14, `BUILD_PLAN.md` §1(개정판) 참조.

**대회 규칙 3(세컨드 화면에 raw stream 실시간 노출)은 여전히 지켜야 합니다.** 단일 Streamlit 배포 안에서 별도 페이지(또는 별도 탭)로 raw trace_event를 폴링해 보여주는 방식으로 만족시킵니다 (`BUILD_PLAN.md` §1 참조).

이 항목들은 **아직 확인되지 않았습니다.** 코드에서 이것들을 사실로 가정하지 말고, 실패 시 폴백 경로를 반드시 두세요.

| # | 전제 | 실패 시 |
|---|---|---|
| 1 | LINER Search API가 한국어 광고 관련 쿼리에서 유효한 결과를 반환 | 영어 쿼리 병행 생성 |
| 2 | LINER 결과의 `date` 필드 커버리지·정확도가 충분 | REFUTED 조건에서 timeframe 요구를 완화, 사람이 읽어 확인 가능한 URL 제시로 축소 |
| 3 | GPT Vision이 한국어 저해상도 광고 캡처를 OCR | 텍스트 붙여넣기 경로를 fallback으로 |
